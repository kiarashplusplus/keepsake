# Geo

Status: `[DONE]` — the seed loads (M1) and the feed queries it (M2); `02144` and `M5V` were
resolved against the live preview stack on 2026-09-06.

Postcode + radius search over US and Canada — no geocoding API. `postal_codes` (D1,
`0002_geo.sql`) is a bundled `country, code -> place_name, admin1, lat, lng` table generated by
`tools/geodata/build-postal-seed.mjs` from GeoNames (~46k rows: US ZIP5, CA FSA, plus a dormant set
of GB outward codes — see below). See [`docs/runbooks/geodata.md`](../runbooks/geodata.md) for
regeneration and loading; CC BY 4.0 attribution is required on the About page wherever this data is
displayed.

**UK is geo-blocked as of 2026-09-06** — a deliberate decision, not a gap. See
[`docs/runbooks/uk-block.md`](../runbooks/uk-block.md) for why and what would have to be true to
lift it. `@keepsake/contracts/geo`'s `COUNTRIES` no longer includes `GB`, so a listing can't claim
to be in the UK and `GET /api/geo/lookup?country=GB` 400s — the seeded GB rows below are inert
data, kept only so re-enabling GB later is cheap. The visitor-facing half of the block
(`apps/api/src/middleware/ukBlock.ts`) is separate and unrelated to this file's normalization
logic.

## Normalization (must match between the seed builder and the query path)

| Country | Rule |
|---|---|
| US | first 5 digits |
| CA | first 3 characters, uppercased — the FSA (Forward Sortation Area) |
| GB (dormant — not in `COUNTRIES`, see above) | outward code (before the space), uppercased |

`apps/api/src/geo/` re-implements the query-time half of this exactly; a drift between the two
means a postcode that resolves in the seed builder 404s at request time.

## Radius query

1. Normalize the input postcode per the table above (or skip straight to step 3 if the client
   passed `lat,lng` directly — "Use my location" on web never round-trips through a postcode).
2. Look up the centroid in `postal_codes`.
3. Compute a bounding box from the radius (default 25 mi; options 10/25/50/100/anywhere).
4. `WHERE status='approved' AND lat BETWEEN ? AND ? AND lng BETWEEN ? AND ?` against the
   `listings_geo` index — the bounding box is the cheap pre-filter.
5. Haversine distance computed in the Worker over the bounding-box result set, sorted by
   distance then `published_at`, bounded offset pagination (max 200).

## Known coarseness (plan Risk #9)

The CA table is FSA level, not full postcode — good enough for radius search, and the `give`
details step shows the resolved place name so a giver can see exactly what "Somerville, MA" or
"M5V" resolved to before publishing. A full-resolution seed swap is a later upgrade, not a blocker,
since the normalization rule (not the schema) is what would need to change. (The dormant GB table
was outward-code level for the same reason, before the UK geo-block took it out of service.)
